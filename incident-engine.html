The problem

Triage was predictable toil

An on-call engineer would get paged, look up the affected service, check runbooks, manually create a ticket, route it to the right team, and notify the rotation — ~30 minutes per incident. Across 20+ incidents/week that's ~10 hours of engineering time each week spent on triage that followed a repeatable pattern — exactly the kind of toil SRE practice says to automate away.

The approach

Event-driven, decoupled, inspectable

Alerts, system events, and health-check failures publish to a central event bus. A config-driven router classifies each event, deduplication suppresses noise from flapping services, and enrichment attaches ownership and runbook context. The ticket engine then handles the full lifecycle — create, route, resolve, notify — while a real-time stream emits structured telemetry so downstream teams react without paging a human.

The results

MTTR and toil, measurably down

Triage time per ticket dropped from ~30 minutes to under a minute, removing ~10 hours/week of on-call toil across 20+ weekly incidents. Tickets now arrive pre-enriched with owner, severity, and runbook links, so responders act instead of investigate. The system has run in production for multiple years through service migrations and on-call rotations.

Tradeoffs & lessons

What running it taught me

Rules-based routing is fast and inspectable but doesn't generalize to novel incident types — it works because the service catalog is stable. Deduplication uses a fixed time window, which occasionally collapses related-but-distinct incidents. Building the system was the easy part; keeping it correct through schema changes, service migrations, and blameless post-mortems is where the real reliability lessons lived.
